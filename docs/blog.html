Java Concurrency in Practice: From Blocking I/O to Virtual Threads

A hands-on walk through every concurrency primitive in the Java ecosystem — sequential baselines, thread pools, bounded queues, lock-free data structures, and virtual threads — built around a real, runnable news aggregator.

NR
NewsRadar Concurrency Handbook · 7-Phase Build · Java 21+ · Maven

In concurrent Java systems, the difference between blocking one thread and blocking ten thousand is the difference between a slow API and a non-functional one. But understanding why — and how to fix it — requires working through each primitive one at a time, with real measurements at every step.

This is the story of NewsRadar: a concurrent RSS news aggregator built from scratch across seven phases. Each phase introduces exactly one new concurrency concept, applies it to a real problem, and produces a measurable result you can see in your terminal.

By the end, we go from a single-threaded blocker that takes nearly 6 seconds to fetch 20 RSS feeds, to a virtual-thread HTTP search API that handles 2,000 concurrent clients at under 2 ms p99.

The Problem With Blocking I/O

In the early days of any service, a sequential fetch loop is sufficient. You read one URL, wait for the response, parse it, move to the next. Simple, correct, easy to debug.

As the service grows, this becomes untenable. A sequential RSS aggregator fetching 20 feeds performs 20 blocking socket reads in series:

Sequential Behavior
URL  1: Fetch (725 ms) → Parse (14 ms)
URL  2: Fetch (420 ms) → Parse ( 9 ms)
URL  3: Fetch (408 ms) → Parse (12 ms)
...
URL 20: Fetch (261 ms) → Parse ( 4 ms)
─────────────────────────────────────
Wall time: 5,890 ms   Sum of fetches: 5,871 ms

Notice the critical detail: wall time equals the sum of all fetch latencies. The CPU was idle for 99.7% of the run, parked on socket reads, waiting for remote servers to respond.

This is the fundamental shape of a blocking I/O bottleneck. It is not a code quality problem. It is a structural one. And it is exactly the problem that concurrency is designed to solve.

Phase 2 — Thread Pool Fetcher: The Classic Win

The fix is straightforward: submit each feed as a Callable<List<Article>> to a fixed-size ExecutorService. Instead of blocking one thread on each fetch sequentially, the pool runs multiple fetches in parallel.

PooledAggregator.java
ExecutorService exec = Executors.newFixedThreadPool(poolSize, namedThreadFactory("fetcher"));
List<Future<TaskResult>> futures = new ArrayList<>();

for (FeedConfig feed : feeds) {
    futures.add(exec.submit(() -> {
        try {
            RawFeed raw = fetcher.fetch(feed);          // blocks this thread
            List<Article> articles = parser.parse(raw);
            return TaskResult.ok(Thread.currentThread().getName(), articles, ...);
        } catch (Exception e) {
            return TaskResult.fail(Thread.currentThread().getName(), ...);
        }
    }));
}

// collect results with per-task timeout
for (Future<TaskResult> f : futures) {
    TaskResult result = f.get(perTaskTimeout.toMillis(), TimeUnit.MILLISECONDS);
    ...
}

// graceful shutdown: drain → wait → force
exec.shutdown();
exec.awaitTermination(30, TimeUnit.SECONDS);
exec.shutdownNow();

The results are dramatic. Running the same 20 feeds through pools of varying sizes:

Thread pool fetcher performance by pool size
Strategy Pool Size Wall Time Articles Speedup
Sequential 1 5,588 ms 509 1.00×
Pooled 4 492 ms 509 11.36×
Pooled 8 291 ms 509 19.20×
Pooled 16 194 ms 509 28.80×
Pooled 32 214 ms 509 26.11×
Key Insight
Pool=32 is slower than pool=16. Once you have more threads than meaningful concurrent workloads, thread-creation overhead and scheduling noise win. For I/O-bound work, the optimal pool size is roughly: min(task count, ~24) — not "more cores = more speed."

There are two speedup numbers worth tracking separately. The headline "28.8×" is the effective wall-time speedup. But the real parallelism number — sum of all fetch latencies divided by wall time — tops out around 6.7× at pool=16. The rest of the gain comes from JVM warm-up: by the time pool=16 runs, DNS is cached, TLS sessions are resumed, and the JIT is warm. This is a real benefit of moving to pooled fetching, but it is not concurrency doing the work.

Phase 3 — Bounded-Queue Pipeline: Decoupling Stages

The thread pool improvement has a structural problem: fetch and parse run on the same thread. A slow parse blocks that thread from picking up the next fetch. More importantly, all 20 Callables sit in the queue simultaneously — fine for 20 feeds, catastrophic for 20,000.

The solution is a producer-consumer pipeline with bounded ArrayBlockingQueues between independent stages.

feeds (20) │ ▼ ┌─────────────────────────────┐ │ fetcher pool (16 threads) │ ← I/O-bound, large pool └──────────────┬──────────────┘ │ rawQueue.put(raw) ← BLOCKS if queue full ▼ ┌────────────────┐ │ rawQueue (cap 8)│ ArrayBlockingQueue<RawFeed> └───────┬─────────┘ │ rawQueue.take() ▼ ┌─────────────────────────────┐ │ parser pool (4 threads) │ ← CPU-bound, ≈ cores └──────────────┬──────────────┘ │ articleQueue.put(article) ▼ ┌─────────────────────┐ │ articleQueue (cap 64)│ ArrayBlockingQueue<Article> └───────┬──────────────┘ │ articleQueue.take() ▼ ┌─────────────────────────────┐ │ indexer (1 thread) │ └─────────────────────────────┘

Three executors, two queues, four control points. The bounded queue is the load-bearing primitive: when the parser pool is saturated, rawQueue.put() parks the calling fetcher thread. Backpressure propagates naturally through the pipeline without any explicit coordination code.

Poison Pills for Clean Shutdown

Stopping producer-consumer pipelines cleanly is notoriously tricky. The right pattern is the poison pill — a sentinel value that signals end-of-stream:

RawFeed.java
public record RawFeed(String feedId, byte[] body, String contentType) {
    // Reference equality (==) — not .equals(). Records auto-generate
    // equals() from values, but a sentinel must be unique by identity.
    public static final RawFeed SHUTDOWN = 
        new RawFeed("__SHUTDOWN__", new byte[0], "__SHUTDOWN__");

    public boolean isShutdown() { return this == SHUTDOWN; }
}

The shutdown sequence: wait for all fetcher futures → put N pills (one per parser thread) → wait for all parser futures → put one pill for the indexer. Each consumer takes exactly one pill and exits voluntarily. No shutdownNow() needed, no interrupted threads mid-write, no lost articles.

Backpressure Caught Live
Tightening the pipeline to --parsers=1 --queue=1 produced 12 fetcher stalls in a real run — fetcher threads parked on rawQueue.put() because the single parser couldn't keep up. The bounded queue isn't decorative; it is a runtime guarantee that memory cannot grow without bound.

Phase 4 — Thread-Safe Inverted Index: Getting Shared State Right

The search index at the core of NewsRadar is a Map<String, Set<ArticleId>> — tokens mapped to the article IDs that contain them. Under concurrent writes from a 16-thread pipeline, three implementations produce very different outcomes.

Implementation 1: UnsafeHashMapIndex (broken)

UnsafeHashMapIndex.java — the race condition
// The classic check-then-act race:
Set<String> set = postings.get(token);
if (set == null) {
    set = new HashSet<>();
    postings.put(token, set);  // Thread B can overwrite A's put here
}
set.add(article.id());         // HashSet itself is not thread-safe

Two threads can both observe null, both create a new HashSet, and one will overwrite the other's entry. Everything added to the first set is silently lost. At high contention, concurrent HashMap resizes can corrupt bucket linked-lists, causing the iterator to visit entries twice — the stress test observed 106 distinct tokens reported when only 100 existed in the vocabulary.

Implementation 2: SynchronizedIndex (correct, slow)

public synchronized void index(Article article) { ... }
public synchronized Set<String> articleIdsFor(String token) { ... }

Every operation acquires the same intrinsic lock. Correct. But with 16 threads, 15 of them are always parked on the monitor. Throughput is bounded by a single serialization point regardless of how many cores you have.

Implementation 3: ConcurrentIndex (correct and scales)

ConcurrentIndex.java
postings.computeIfAbsent(token, k -> ConcurrentHashMap.newKeySet())
        .add(article.id());

Three carefully chosen primitives:

ConcurrentHashMap — each internal bin has its own lock. Writers to different tokens never contend at all.

computeIfAbsent — atomic check-and-create. The get/put race that breaks the unsafe version cannot happen: at most one Set is ever created per token.

ConcurrentHashMap.newKeySet() — a thread-safe Set backed by CHM's own fine-grained locking. Concurrent add calls on the same key set use the same bucket-level locking as the outer map.

Stress test results — 16 threads × 50,000 articles × 20 tokens, 100-token vocabulary:

Thread-safe index implementation comparison
Implementation Correct? Tokens Postings Elapsed ops/sec
UnsafeHashMapIndex NO 106 995,859 82 ms 12,144,621
SynchronizedIndex yes 100 1,000,000 430 ms 2,325,581
ConcurrentIndex yes 100 1,000,000 165 ms 6,060,606
The Lesson
The unsafe index's 12M ops/sec is meaningless — it is garbage-fast, producing results that cannot be trusted. The "correct?" column gates everything else. A broken data structure that runs faster is not better; it is just broken faster.

Phase 5 — HTTP Search API on Virtual Threads

The SearchableIndex wraps the concurrent index behind a ReentrantReadWriteLock. Individual reads and writes go directly to the CHM-backed internals (no lock needed there). The read-write lock only guards whole-index swaps — replacing both the index and the article map atomically when Phase 6's scheduled refresh fires.

SearchableIndex.java — asymmetric locking
public List<Article> search(String query, int limit) {
    lock.readLock().lock();             // many readers can hold this simultaneously
    try {
        InvertedIndex idx = this.index;   // snapshot refs atomically
        Map<String, Article> arts = this.articles;
        // AND-semantics: intersect posting sets for each query token
        ...
    } finally { lock.readLock().unlock(); }
}

public void swap(InvertedIndex newIndex, Map<String, Article> newArticles) {
    lock.writeLock().lock();            // rare; blocks all readers briefly
    try {
        this.index = newIndex;
        this.articles = newArticles;
        this.lastRefresh = Instant.now();
    } finally { lock.writeLock().unlock(); }
}

The HTTP server uses a single line to swap from a platform-thread pool to Java 21 virtual threads:

SearchServer.java
server = HttpServer.create(new InetSocketAddress(port), /* backlog */ 1024);
server.setExecutor(Executors.newVirtualThreadPerTaskExecutor());
server.createContext("/search", new SearchHandler(index, json));
server.createContext("/health", new HealthHandler(index, refresher, json));
server.start();

Each request gets its own virtual thread. The handler code is plain blocking Java — no callbacks, no reactive plumbing. The runtime makes blocking cheap by mounting virtual threads on a small pool of carrier threads and unmounting them when they park on I/O.

Load test results — varying client concurrency against the same server:

1,000 1,257 ms 1,000 796 req/s 836 µs 1,173 µs

At 2,000 simultaneous virtual threads, every request completes successfully in under 2 ms p99. The JVM held 2,000 virtual threads — each parked on its outbound socket — multiplexed over a small carrier pool. Try this with Executors.newFixedThreadPool(2000) and you would burn roughly 2 GB of stack memory before issuing the first request.

At 5,000 clients, 1,827 requests fail with ConnectException. The virtual threads were not the bottleneck — the OS kernel listen queue overflowed. The fix is persistent connections (HTTP/2) or capping in-flight requests via a Semaphore. The JVM needed no changes.

Phase 6 — Scheduled Refresh and Graceful Shutdown

A real service re-indexes periodically. Phase 6 wires a ScheduledExecutorService that rebuilds the full index off-line every 30 seconds and swaps it in atomically:

ScheduledRefresher.java
handle = scheduler.scheduleAtFixedRate(
    this::refresh, 0, interval.toMillis(), TimeUnit.MILLISECONDS);

private void refresh() {
    refreshing.set(true);
    try {
        // Build a new index off-line — readers hit the current one uninterrupted
        InvertedIndex freshIndex = new ConcurrentIndex();
        Map<String, Article> freshArticles = new ConcurrentHashMap<>();
        for (Article a : pipeline.run(feeds).articles()) {
            freshIndex.index(a);
            freshArticles.put(a.id(), a);
        }
        target.swap(freshIndex, freshArticles);    // atomic under write lock
    } finally {
        refreshing.set(false);
        firstRefreshLatch.countDown();             // CountDownLatch: fire once, wake all waiters
    }
}

A CountDownLatch(1) gates server startup: the main thread blocks on awaitFirstRefresh() until the index is populated. The search endpoint never returns empty results during a cold start.

Shutdown runs in reverse dependency order — stop accepting requests, cancel the schedule, await any in-flight refresh, drain pools:

Shutdown sequence
server.stop();         // 1. close socket, drain in-flight exchanges
refresher.stop();      // 2. cancel schedule, awaitTermination(30s)
                       // 3. each pool does shutdown() → awaitTermination → shutdownNow()

Phase 7 — JMH Benchmarks: Measure, Not Guess

The final phase is a suite of JMH microbenchmarks that isolate each architectural decision and measure it with rigorous methodology. The most important finding is also the most counterintuitive.

The Critical Lesson
In the JMH benchmark, the pipeline is slower than sequential. The stub fetcher returns bytes instantly — zero network latency. Without I/O wait, the bounded-queue overhead (two ArrayBlockingQueue put/take round-trips per item, poison-pill coordination, multiple pool shutdowns) adds cost with no benefit. The real-world 28× speedup came entirely from overlapping network waits — not from CPUs running faster.

This is why benchmarks matter. "Thread pools and pipelines are fast" is the wrong mental model. The correct mental model is: thread pools and pipelines eliminate wasted wait time. If there is no wait time to eliminate, they add overhead.

Tradeoffs and Design Considerations

While each primitive is powerful in its domain, the choices are not free:

Pool sizing for I/O

I/O-bound pools are not sized by core count — they are sized by meaningful concurrent in-flight requests. Beyond the task count, extra threads add scheduling noise with no throughput gain.

Bounded vs. unbounded queues

An unbounded LinkedBlockingQueue with no capacity limit will grow until the heap exhausts. Always use ArrayBlockingQueue with an explicit capacity for production pipelines.

ReadWriteLock vs. synchronized

ReadWriteLock only pays off when reads vastly outnumber writes. For a search API with one refresh per 30 seconds and thousands of searches, it is the correct choice. For a write-heavy store, the cost of acquiring the write lock is high.

Virtual threads vs. platform threads

Virtual threads are not faster at CPU work — they are cheaper at blocking. If your workload is CPU-bound, a ForkJoinPool sized to core count outperforms a virtual-thread executor.

Conclusion

Concurrency in Java is not a single tool — it is a toolkit matched to workload shape. The same 20-feed aggregator went from 5,588 ms (sequential) to 194 ms (thread pool) not because of faster hardware, but because the workload was almost entirely I/O wait that could be parallelized.

Each phase of this build tells a concrete story: sequential proves the problem. Thread pools show the win. Bounded queues prove the safety guarantee. Three index implementations prove what correctness costs. Virtual threads prove that blocking I/O is no longer a resource constraint in Java 21+. And JMH proves that every one of these claims needs a measurement — because intuition about concurrent performance is reliably wrong.

Whether you are building a news aggregator, a machine learning ingestion pipeline, or a high-throughput API, these are the same patterns and the same tradeoffs. The correct starting point is always the same: measure the baseline, identify where the time is spent, and pick the primitive that addresses that specific cost.
